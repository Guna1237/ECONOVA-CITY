# ECONOVA: CITY
# VISUAL SYSTEM

Version: 1.0
Status: Design Source of Truth

---

# 1. PURPOSE

This document defines the complete visual and interaction direction for ECONOVA: CITY.

It is the visual source of truth for every frontend, projector, player interface, animation, component, illustration, icon, and visual effect.

The goal is not to make ECONOVA look like a generic website, dashboard, finance app, or college project.

The goal is to make it feel like a polished, premium multiplayer strategy game that happens to run in a browser.

The visual experience must communicate:

- strategy
- competition
- a living city
- changing economic conditions
- ownership
- growth
- risk
- decisions
- momentum
- achievement

The interface must look impressive immediately while remaining extremely easy to understand during live gameplay.

---

# 2. PRIMARY VISUAL GOAL

The first impression should be:

"That looks like an actual game."

Not:

"That looks like a website."

Not:

"That looks like Excel."

Not:

"That looks like a financial dashboard."

Not:

"That looks like a Monopoly clone."

ECONOVA should have its own visual identity.

The visual language should combine:

- premium strategy game presentation
- modern city aesthetics
- economic/market signals
- elegant information design
- strong cinematic moments
- clean mobile interaction

The design should feel modern rather than futuristic for the sake of being futuristic.

Do not use cyberpunk styling merely because it is visually impressive.

Do not use excessive neon.

Do not use unnecessary 3D.

Do not use visual effects that interfere with gameplay.

---

# 3. DESIGN PRINCIPLES

Every visual decision should follow these principles.

## 3.1 CLARITY FIRST

Players must understand what is happening immediately.

Visual hierarchy is more important than decoration.

Important information must always be easier to see than secondary information.

---

## 3.2 GAME FIRST

The interface should feel like a game.

Use:

- meaningful state changes
- visual feedback
- animated transitions
- game-like cards
- map elements
- ownership indicators
- event presentations
- satisfying confirmations

Avoid making the experience feel like a CRUD application.

---

## 3.3 PREMIUM, NOT OVERDESIGNED

Premium does not mean adding more effects.

Premium means:

- consistent spacing
- deliberate typography
- strong composition
- high-quality assets
- controlled animation
- excellent hierarchy
- consistent components
- smooth interaction
- attention to detail

Every visual element should have a purpose.

---

## 3.4 INFORMATION DENSITY WITH ORDER

ECONOVA contains significant information.

Do not remove useful information merely to make the interface minimal.

Instead:

- group related information
- create hierarchy
- use progressive disclosure
- use visual emphasis
- separate public and private information
- keep important actions obvious

---

## 3.5 CONSISTENCY

A property card should feel like it belongs to the same system as:

- a strategy card
- a Breaking News panel
- a policy panel
- a player profile
- a scoreboard
- the city map

Do not create unrelated visual styles for different features.

---

## 3.6 RESPONSIVENESS

Interactions must feel immediate.

When a player performs an action:

1. The interface acknowledges the input immediately.
2. The server validates the action.
3. The confirmed state is displayed.
4. Appropriate visual feedback occurs.

Never create an interaction that feels frozen while waiting for a server response.

Do not falsely display an action as completed before authoritative confirmation.

---

# 4. VISUAL PERSONALITY

ECONOVA should feel:

- intelligent
- competitive
- energetic
- premium
- modern
- strategic
- urban
- slightly cinematic
- approachable

It should NOT feel:

- childish
- corporate
- overly academic
- gambling-oriented
- overly futuristic
- cluttered
- sterile
- cartoonish
- like a banking application

The visual language should work for an 18–22 year old university audience while still looking professionally designed.

---

# 5. BRAND DIRECTION

The product name is:

ECONOVA: CITY

Use the name prominently but intelligently.

Do not place the logo everywhere.

The primary title treatment should be:

ECONOVA
CITY

or:

ECONOVA: CITY

depending on the available space.

The brand should be recognizable from the projector from a distance.

The title should not dominate active gameplay screens.

---

# 6. COLOR SYSTEM

Use a controlled color system.

Do not allow individual components to invent their own colors.

The exact final color values may be refined during visual implementation, but the following semantic structure must remain.

## 6.1 BASE COLORS

Use a sophisticated dark primary environment.

Primary background:

- deep charcoal / near-black

Secondary background:

- slightly lighter dark surface

Tertiary surface:

- elevated panel surface

Do not use pure black everywhere.

There must be enough separation between:

- background
- cards
- panels
- overlays
- active elements

---

## 6.2 TEXT COLORS

Primary text:

- bright, highly readable

Secondary text:

- muted but clearly readable

Tertiary text:

- reserved for low-priority information

Never use extremely low-contrast text merely for aesthetic purposes.

Projector readability takes priority.

---

## 6.3 SEMANTIC COLORS

Use semantic colors consistently.

Positive:

- green family

Negative:

- red family

Warning:

- amber/yellow family

Information:

- blue family

Neutral:

- gray family

These colors should communicate meaning, not decoration.

Do not use red merely because it looks dramatic.

Do not use green merely because it looks attractive.

---

# 7. DISTRICT COLORS

Each district may have its own visual identity.

District colors should be:

- distinct
- readable
- sophisticated
- compatible with the overall dark UI

District colors must remain recognizable across:

- map
- property cards
- property markers
- filters
- charts
- event cards

Do not use four extremely bright colors that make the city look like a children's board game.

District colors should support hierarchy rather than overpower it.

---

# 8. PLAYER COLORS

Player colors must be immediately distinguishable.

Player colors should appear in:

- ownership markers
- player tokens
- leaderboard
- player identity
- relevant property indicators

Player colors must remain distinguishable for users with common forms of color-vision deficiency.

Do not rely on color alone.

Combine player color with:

- icon
- initials
- pattern
- marker shape
- player number

where necessary.

---

# 9. TYPOGRAPHY

Use a modern, highly legible sans-serif typeface.

Typography should have clear levels:

## Display

Used for:

- ECONOVA title
- major round announcements
- major event announcements
- final winner presentation

## Heading

Used for:

- sections
- districts
- panels
- important labels

## Body

Used for:

- descriptions
- rules
- explanatory text

## UI

Used for:

- buttons
- values
- status
- property information
- player information

## Numeric

Important numbers should have strong visual treatment.

Examples:

- credits
- Influence
- round
- demand
- property values
- final score

Numbers must be easy to scan.

---

# 10. TYPOGRAPHY RULES

Never use more than a small number of typefaces.

Prefer one primary family with multiple weights.

Do not use decorative fonts for normal information.

Do not use all-caps for large amounts of body text.

All-caps may be used for:

- small labels
- categories
- status indicators
- short headings

Do not use excessively thin typography.

Projector text must remain readable at a distance.

---

# 11. SPACING

Use a consistent spacing scale.

Components should feel intentionally aligned.

Avoid:

- random margins
- inconsistent card padding
- inconsistent button heights
- cramped text
- large unexplained empty spaces

The design should use a predictable layout rhythm.

All major components should align to an underlying spacing system.

---

# 12. CORNER RADIUS

Use a consistent radius system.

Do not make every element heavily rounded.

Recommended visual hierarchy:

- small controls: modest radius
- cards: medium radius
- large panels: medium/large radius
- major overlays: larger radius where appropriate

Avoid the "everything is a pill" aesthetic.

Buttons should not all look like capsules.

---

# 13. BORDERS AND SURFACES

Use subtle borders to establish hierarchy.

Panels should be distinguishable from the background without requiring huge shadows.

Prefer:

- subtle borders
- controlled surface contrast
- restrained shadows
- occasional glow for important state

Avoid:

- giant drop shadows
- excessive glass effects
- excessive blur
- glowing borders around everything

---

# 14. GLASS / TRANSPARENCY

Glass effects may be used selectively.

Good uses:

- major overlays
- event announcements
- modal confirmations
- cinematic moments

Bad uses:

- every card
- every button
- every panel
- information-dense tables

Text readability always wins over visual effects.

---

# 15. ICONOGRAPHY

Use one consistent icon system.

Icons should be:

- simple
- recognizable
- modern
- consistent in stroke/weight
- readable at small sizes

Do not mix unrelated icon styles.

Avoid using emojis as core UI icons.

Icons should support text, not replace important text where ambiguity could occur.

---

# 16. THE CITY MAP

The city map is the visual centerpiece of ECONOVA.

It should not look like a spreadsheet.

It should visually communicate:

- districts
- properties
- ownership
- development
- city structure
- movement/progression where applicable
- economic activity

The map should feel like a stylized strategic city rather than a literal geographic map.

---

# 17. CITY MAP STYLE

The city can use a:

- 2D
- 2.5D
- stylized isometric

presentation.

Choose whichever provides the best combination of:

- visual quality
- performance
- readability
- implementation reliability

Do not use full 3D merely because it is possible.

The city should remain readable on a projector.

---

# 18. CITY DISTRICTS

Districts should have distinct visual zones.

Each district should be recognizable through:

- color
- architecture/theme
- label
- layout
- iconography

Districts should not require players to memorize complicated visual differences.

The map should make ownership and development easy to identify.

---

# 19. PROPERTIES

Properties are important game objects.

A property should have a strong visual representation.

A property may visually communicate:

- name
- district
- ownership
- development level
- current economic status
- relevant value

Do not overload the property itself with every piece of information.

Use the property card/detail panel for deeper information.

---

# 20. PROPERTY DEVELOPMENT

Development should be visually satisfying.

When a property increases in development:

- show the new development visually
- animate the transition
- update the relevant value
- communicate the successful action

Possible representations:

- larger building
- additional floors
- additional structures
- stronger lighting
- upgraded property marker

Do not make development purely a number change.

Players should be able to look at the city and understand that it has grown.

---

# 21. OWNERSHIP

Ownership must be instantly recognizable.

Use:

- player-colored marker
- player initials/icon
- subtle property outline
- ownership indicator

Avoid covering the entire property in a bright player color.

The underlying district identity should remain visible.

---

# 22. DEMAND

Demand should feel like a living part of the city.

Use:

- directional indicators
- movement
- subtle pulses
- compact graphs
- arrows
- visual changes

Examples:

Increasing demand:

`↑`

Decreasing demand:

`↓`

Stable:

`→`

Do not rely exclusively on red/green.

The direction and numerical value should both be understandable.

---

# 23. MARKET / ECONOMIC SIGNALS

Economic information should look dynamic without becoming a stock-trading interface.

Use:

- compact charts
- trend indicators
- demand markers
- numerical values
- animated transitions

Avoid overly complex financial charts.

The game should be understandable by someone who has never studied finance.

---

# 24. PLAYER DASHBOARD

The player dashboard is private.

It should immediately communicate:

1. Who am I?
2. How many credits do I have?
3. What do I own?
4. What can I do now?
5. What private information do I have?
6. What is waiting for my decision?

The most important action should be visually obvious.

---

# 25. PLAYER DASHBOARD HIERARCHY

Recommended order:

```text
PLAYER IDENTITY

CURRENT RESOURCES

CURRENT TURN / GAME STATUS

AVAILABLE ACTIONS

PROPERTIES

PRIVATE CARDS

SECRET OBJECTIVE

OTHER INFORMATION
```

Do not make players scroll past unnecessary decorative elements before reaching an action.


---

26. PRIMARY ACTIONS

Important actions should have strong visual hierarchy.

Examples:

Buy

Develop

Trade

Play Card

Vote

Confirm

End Turn


Primary actions:

visually prominent

clearly labelled

easy to tap

immediately responsive


Secondary actions:

less prominent


Dangerous/destructive actions:

clearly differentiated

require confirmation when appropriate



---

27. BUTTONS

Buttons should communicate state.

States include:

default

hover

pressed

disabled

loading

success

error


A disabled button must look disabled.

A loading button must not allow duplicate submissions.

Do not use animations that make a button feel delayed.


---

28. PROPERTY CARDS

Property cards should feel collectible and strategic.

They should have:

clear name

district identity

important value

development information

ownership status

action options where appropriate


The visual design should be reusable across the entire property system.

Avoid making each property card visually unrelated.


---

29. STRATEGY CARDS

If strategy/event cards exist, they should feel like physical game cards translated into digital form.

Use:

strong title

clear category

concise effect

visual identity

readable action

clear state


Cards may use subtle hover/press animations.

Do not hide critical rules behind an animation.


---

30. SECRET OBJECTIVES

Secret objectives must visually communicate privacy.

They should feel distinct from public information.

Use a subtle private-information treatment.

Do not use an excessively obvious "SECRET!!!" visual that could reveal information from a player's screen.

The projector must never reveal private objectives.


---

31. TRADING INTERFACE

Trading is primarily a social interaction.

The software should facilitate the transaction rather than replace face-to-face negotiation.

The interface should make it easy to:

select assets

review the offer

confirm

reject

finalize


Do not build an unnecessary private messaging system.

Do not make players negotiate through chat.


---

32. EVENT PRESENTATION

Breaking News and major events are important cinematic moments.

When an event occurs:

1. Briefly interrupt normal visual hierarchy.


2. Display the event prominently.


3. Explain the effect clearly.


4. Animate relevant changes.


5. Return to the normal game state.



Example structure:

BREAKING NEWS

METRO EXPANSION APPROVED

Mobility demand increases.

[visual impact]

Continue

Do not keep players waiting through long animations.


---

33. POLICY / CITY COUNCIL

Council moments should feel important.

The visual sequence may be:

POLICY PROPOSED
        ↓
PLAYER VOTING
        ↓
VOTES LOCKED
        ↓
REVEAL
        ↓
RESULT
        ↓
CITY EFFECT

Use animation to create anticipation.

Keep the actual information extremely clear.


---

34. TURN TRANSITIONS

A turn change should be visually obvious.

The active player should be clearly indicated.

A good transition may include:

player name

player marker

short animation

action availability


Do not use a long cinematic transition every turn.

Turn transitions should be fast.


---

35. ROUND TRANSITIONS

Round transitions can be more cinematic than turn transitions.

Possible structure:

ROUND 5

THE CITY IS CHANGING

[market/demand summary]

CONTINUE

Show the most important changes.

Do not make players read a wall of text.


---

36. WINNER / END GAME

The end game should feel rewarding.

The final sequence should communicate:

game complete

final scores

rankings

major achievements

winner

final city state


Use a short cinematic presentation.

The winner should be visually prominent.

Do not make the final screen look like a simple database table.


---

37. LEADERBOARD

The leaderboard should prioritize readability.

Show:

rank

player

relevant score

important secondary metric where appropriate


The current player should be easy to identify.

Do not show unnecessary statistics during active gameplay.


---

38. PROJECTOR DESIGN

The projector is a public screen.

Design specifically for:

16:9

1920x1080

viewing from distance

potentially imperfect projector quality

varying room lighting


Do not design for a laptop first and simply stretch it onto the projector.

The projector layout should be deliberately composed for large-screen viewing.


---

39. PROJECTOR INFORMATION HIERARCHY

The projector should prioritize:

1. Current round


2. Current player


3. Major game state


4. City map


5. Important economic information


6. Current event/policy


7. Public standings



Private information must never appear.


---

40. PROJECTOR READABILITY

Use:

large text

strong contrast

limited small labels

clear grouping

strong spacing


Avoid:

tiny text

dense tables

thin fonts

low contrast

excessive decorative UI

excessive motion


The test is:

Can someone standing several metres away understand what is happening?

If not, redesign it.


---

41. MOBILE PLAYER DESIGN

Player screens should be designed mobile-first.

Target common smartphone dimensions.

Do not assume:

large screen

mouse

keyboard

perfect connection


Touch interactions must be comfortable.

Important controls should generally be reachable without excessive precision.


---

42. MOBILE ORIENTATION

The game should work primarily in portrait mode for player devices unless a specific screen requires otherwise.

Do not force landscape unnecessarily.

The projector remains landscape.


---

43. RESPONSIVE BREAKPOINTS

Use responsive layouts rather than fixed desktop layouts scaled down.

The interface should adapt intelligently.

Do not simply shrink:

text

buttons

cards


Instead change layout structure where necessary.


---

44. LOADING STATES

Every asynchronous state must have a clear visual state.

Examples:

joining room

connecting

reconnecting

loading game

submitting action

waiting for server

waiting for another player


Avoid blank screens.

Avoid indefinite spinners without context.


---

45. CONNECTION STATUS

Players should know when their connection is unhealthy.

Use a subtle but clear status indicator.

Possible states:

Connected

Connecting

Reconnecting

Offline


Do not constantly distract players with network information when everything is working.

Only emphasize connection problems when they matter.


---

46. ERROR STATES

Errors must be understandable.

Bad:

WebSocket Error 1006

Better:

Connection lost. Reconnecting...

For an invalid action:

You can't buy this property right now.

Where useful, explain why.

Never expose technical server errors to normal players.


---

47. CONFIRMATIONS

Important irreversible actions may require confirmation.

Examples:

finalizing a trade

using an important card

ending a turn


Do not require confirmation for every minor action.

Too many confirmations slow the game down.


---

48. MICROINTERACTIONS

Use subtle microinteractions for:

button press

card selection

property selection

successful action

resource change

status update


Microinteractions should reinforce cause and effect.

They should not become distractions.


---

49. ANIMATION SYSTEM

Use a consistent animation language.

Animation categories:

Instant

For:

minor state updates

simple labels

small UI changes


Fast

For:

button feedback

card selection

small panels

confirmations


Medium

For:

property updates

demand changes

turn transitions


Cinematic

For:

major events

Council results

final scoring

winner presentation


Avoid arbitrary animation durations.

Create reusable timing tokens.


---

50. ANIMATION PERFORMANCE

Prefer GPU-friendly transforms and opacity changes where possible.

Avoid unnecessary:

layout thrashing

continuous JavaScript animation loops

expensive blur

large particle systems

high-resolution video backgrounds

huge animated DOM trees


Animations must maintain smoothness on the actual event hardware.

If an effect causes frame drops, simplify it.


---

51. REDUCED MOTION

Respect reduced-motion preferences where practical.

Users who request reduced motion should still receive clear state feedback.

Replace cinematic motion with:

fades

state changes

static indicators


where necessary.


---

52. SOUND

Sound is optional and must never be required for understanding.

If implemented:

keep it subtle

provide mute controls

use sound for important events

do not use constant background noise

do not rely on sound to communicate critical information


The game must remain completely playable without sound.


---

53. ASSET STYLE

All illustrations and assets should feel like they belong to the same world.

Avoid mixing:

realistic photography

cartoon illustrations

unrelated 3D renders

random stock images

inconsistent icon packs


Prefer a coherent custom visual language.


---

54. ICONS VS ILLUSTRATIONS

Icons are for:

actions

categories

status

navigation


Illustrations are for:

major events

city identity

district identity

cinematic moments


Do not use illustrations where an icon is clearer.

Do not use icons where a visual scene would improve the experience.


---

55. BACKGROUNDS

Backgrounds should establish atmosphere without competing with information.

Possible techniques:

subtle city silhouettes

architectural forms

controlled gradients

faint map geometry

restrained texture

atmospheric lighting


Do not use visually noisy backgrounds behind dense information.


---

56. DATA VISUALIZATION

Charts must answer a question.

Good:

demand increased

demand decreased

property value changed

district is performing strongly


Bad:

complicated charts with no gameplay purpose

tiny labels

unnecessary axes

decorative graphs


Keep charts simple enough for a casual player to understand.


---

57. ACCESSIBILITY

Accessibility is part of visual quality.

Ensure:

sufficient contrast

readable text

touch-friendly controls

clear focus states

semantic labels

keyboard usability where relevant

reduced motion support

information not communicated only through color


Important game states must have more than one visual cue where appropriate.


---

58. EMPTY STATES

Empty states should feel intentional.

Examples:

No properties:

You don't own any properties yet.

No available action:

No actions available right now.

No cards:

No strategy cards available.

Avoid blank panels.


---

59. DISABLED STATES

Disabled controls must communicate why they are unavailable when useful.

Example:

BUILD

Disabled because:

Requires sufficient credits

Do not make disabled buttons look like broken UI.


---

60. RESPONSIVE PROJECTOR / PLAYER SEPARATION

Do not treat the projector as merely another responsive breakpoint of the player interface.

They are different products.

Projector

Public, cinematic, observational.

Player

Private, interactive, action-focused.

Admin

Operational, controlled, information-heavy.

Each should share the same design system but have different layouts.


---

61. ADMIN INTERFACE

The admin panel should prioritize reliability over visual spectacle.

It must clearly show:

room

game status

players

current turn

connection status

round

important state

controls

errors


Admin actions should be obvious and safely separated from normal information.

Dangerous actions should require confirmation.


---

62. ADMIN VISUAL STYLE

The admin panel can be more utilitarian.

Do not waste development time making it as cinematic as the projector.

It still must be:

clean

readable

reliable

fast

difficult to misuse



---

63. VISUAL STATE MACHINE

Important UI states should be explicitly designed.

For example:

LOBBY
  ↓
STARTING
  ↓
ACTIVE
  ↓
ACTION
  ↓
RESOLVING
  ↓
UPDATED
  ↓
NEXT TURN

Every state should have a deliberate visual presentation.

Do not rely on accidental combinations of components.


---

64. VISUAL FEEDBACK FOR SERVER ACTIONS

When an action is submitted:

USER INPUT
    ↓
SUBMITTING
    ↓
SERVER RESPONSE
    ↓
SUCCESS / FAILURE

The UI must distinguish:

request sent

request accepted

request rejected


Do not display a false success state.


---

65. STATE SYNCHRONIZATION VISUALS

When the server updates state:

animate only the affected elements where practical

avoid re-rendering the entire screen unnecessarily

preserve user context

avoid sudden layout jumps


Example:

If demand changes for Mobility:

Only the relevant demand indicator and affected elements should visibly update.

Do not make the entire UI flash.


---

66. VISUAL PRIORITY DURING LIVE PLAY

During active gameplay:

GAMEPLAY > INFORMATION > ATMOSPHERE > DECORATION

Never reverse this.

A beautiful animation that hides the player's available action is bad design.


---

67. NO VISUAL GAMBLING LANGUAGE

ECONOVA uses fictional in-game City Credits.

The interface must not visually imply real-money gambling.

Avoid:

casino aesthetics

poker-table aesthetics

betting language

slot-machine effects

gambling UI patterns


The visual identity should communicate strategy and economic decision-making.


---

68. NO MONOPOLY CLONE

ECONOVA may use familiar strategy-game conventions, but the visual identity must be original.

Do not copy:

Monopoly board styling

Monopoly typography

Monopoly property card design

Monopoly branding

Monopoly colors

Monopoly characters

Monopoly visual assets


ECONOVA must look like its own product.


---

Create reusable components.

Examples:

Button

IconButton

PlayerBadge

DemandIndicator

DistrictBadge

EventCard

ObjectiveCard

Do not create one-off versions of the same component unnecessarily.


---

70. COMPONENT CONSISTENCY

If the same concept appears in multiple locations, reuse the same component or design primitive.

For example:

Player identity should not look different on:

projector

leaderboard

player dashboard

trade interface


The scale may change, but the visual language should remain consistent.


---

71. DESIGN TOKENS

Centralize:

colors

typography

spacing

radii

shadows

transitions

animation durations

breakpoints


Do not hardcode random visual values throughout the application.

The design system should be easy to refine globally.


---

72. NO MAGIC VISUAL VALUES

Avoid situations where:

one card uses 17px padding

another uses 19px

another uses 23px


unless there is a deliberate reason.

Use design tokens.

Consistency creates polish.


---

73. VISUAL QA

Every major visual feature should be tested at minimum in:

1920x1080 projector layout

common mobile viewport

desktop browser

narrow mobile viewport


Check:

text overflow

clipping

spacing

contrast

animation

loading states

error states

disabled states

long names

large numbers

unexpected game states



---

74. PROJECTOR QA

Physically test the projector experience.

Do not only test it on a laptop screen.

Check:

viewing distance

brightness

contrast

readability

color accuracy

animation smoothness

transitions

map clarity


If important text cannot be read from the audience area, redesign it.


---

75. PERFORMANCE QA

Visual implementation is not complete until it has been checked for performance.

Look for:

dropped frames

excessive CPU usage

excessive GPU usage

memory growth

large bundle size

slow initial load

excessive WebSocket updates

unnecessary re-renders


Do not assume a powerful development computer represents the event environment.


---

76. VISUAL REGRESSION

When practical, maintain screenshots or browser-based visual checks for important screens.

Important screens include:

lobby

projector game board

player dashboard

property detail

trade

event

policy vote

leaderboard

final results

admin


Major visual changes should be deliberate.


---

77. DESIGN REVIEW CHECKLIST

Before approving a major visual feature, ask:

Does it look like ECONOVA?

Is the hierarchy clear?

Is it readable?

Is it visually consistent?

Does it work on mobile?

Does it work on projector?

Is the interaction obvious?

Is the animation useful?

Does it remain smooth?

Does it communicate state correctly?

Does it expose private information?

Does it add unnecessary complexity?


If several answers are no, revise the feature.


---

78. ANIMATION REVIEW CHECKLIST

Before adding an animation:

1. What state change does it communicate?


2. Does it improve understanding?


3. Does it delay gameplay?


4. Does it affect performance?


5. Does it work on weaker hardware?


6. Does it remain readable?


7. Is there already an animation pattern for this?



If the only answer is "because it looks cool," reconsider it.


---

79. VISUAL DEVELOPMENT ORDER

Build visual systems in this order:

1. Global design system


2. Typography


3. Colors


4. Layout primitives


5. Core components


6. Player dashboard


7. Projector shell


8. City map


9. Property visuals


10. Game-state animations


11. Events


12. Council/policy presentation


13. End-game presentation


14. Admin interface


15. Final polish



Do not polish individual screens before the underlying design system is stable.

80. FRONTEND IMPLEMENTATION RULE

The frontend must consume authoritative game state.

Do not hardcode gameplay state merely to make the UI look correct.

Mock data may be used during isolated visual development, but it must be clearly separated from production game state.

Before integration, replace mock state with actual server-driven state.


---

81. VISUAL DEVELOPMENT WITH AI AGENTS

AI agents working on visuals must:

1. Read this document.


2. Inspect existing components.


3. Reuse the design system.


4. Avoid unrelated backend changes.


5. Avoid changing game rules.


6. Test the actual browser experience.


7. Check performance.


8. Record significant visual decisions.


9. Avoid introducing duplicate components.


10. Preserve existing functionality.



Do not allow an AI agent to redesign the entire application merely because it prefers another aesthetic.


---

82. FINAL VISUAL STANDARD

The final product should satisfy all of the following:

FIRST IMPRESSION

Looks like a real game.

PROJECTOR

Readable, cinematic and visually impressive.

PLAYER

Fast, intuitive and beautiful on a phone.

ADMIN

Clear, safe and reliable.

ANIMATION

Smooth and purposeful.

INFORMATION

Dense but understandable.

BRAND

Distinctive and consistent.

PERFORMANCE

No noticeable lag during normal gameplay.

ACCESSIBILITY

Readable and usable.

CONSISTENCY

Every major screen feels like the same product.


---

83. NON-NEGOTIABLE RULES

1. Never sacrifice readability for aesthetics.


2. Never sacrifice game responsiveness for animation.


3. Never expose private player information on public screens.


4. Never create inconsistent component styles without a deliberate reason.


5. Never introduce heavy visual effects without testing performance.


6. Never use random stock assets that conflict with the visual identity.


7. Never make the game look like a generic dashboard.


8. Never make the game look like a direct Monopoly clone.


9. Never rely solely on color to communicate critical information.


10. Never fake a successful server action.


11. Never make the player wait unnecessarily for decorative animations.


12. Never redesign unrelated screens during a focused UI task.


13. Never modify gameplay rules from the visual layer.


14. Never prioritize visual spectacle over event-day reliability.


15. The final visual experience must be impressive AND usable.




---

84. FINAL DESIGN TEST

Before considering the visual system complete, answer:

If someone walks past the projector for five seconds:

Can they tell that this is a game?

Can they tell that multiple players are competing?

Can they tell that it is happening in a city?

Can they understand who is currently playing?

Can they see that the city is changing?

Can they tell that decisions have consequences?

If a player picks up their phone:

Can they immediately tell who they are?

Can they see what they own?

Can they see what they can do?

Can they understand what happens after pressing an action?

If the answer to these questions is yes, the visual system is doing its job.

The goal is not simply to make ECONOVA beautiful.

The goal is to make the game state itself beautiful, understandable and exciting.
